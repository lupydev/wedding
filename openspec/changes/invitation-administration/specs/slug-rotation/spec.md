# Slug Rotation Specification

## Purpose

Rotating a dispatched invitation's slug, as the exit for "dispatched by
mistake": what a rotation changes, what it invalidates, and what it does NOT
and cannot undo. This is a new capability; it has no baseline to supersede. The
`slug_rotated_at` column it operates against was designed but never
implemented before this change.

## Requirements

### Requirement: Rotation replaces the slug and records when

Rotating an invitation MUST assign it a NEW slug, generated by the same
opaque, random, URL-safe generation rule as invitation creation, and MUST
record the moment of rotation. The invitation's identity (its row, its guests,
its greeting name, its RSVP history, its dispatch history) MUST be unaffected;
only the slug — and therefore the URL that reaches it — changes.

#### Scenario: Rotation assigns a new, distinct slug

- GIVEN an invitation with slug `k7q2m9xr4t`
- WHEN the slug is rotated
- THEN the invitation MUST be assigned a new slug different from `k7q2m9xr4t`, generated with the same entropy and character-set guarantee as a freshly created invitation

#### Scenario: Rotation preserves everything but the slug

- GIVEN an invitation with existing guests, a greeting name, and RSVP history
- WHEN the slug is rotated
- THEN the invitation's guests, greeting name, and RSVP history MUST be unchanged; only the slug and the rotation timestamp differ

### Requirement: The old slug stops resolving

Once rotated, the OLD slug MUST NOT resolve to the invitation. A request for
the old slug MUST be handled exactly as an unknown slug is handled elsewhere in
this project — a friendly contact page, never a raw 404 and never the
invitation's content.

#### Scenario: The old slug shows the friendly unknown-slug page

- GIVEN an invitation was dispatched at slug `k7q2m9xr4t` and later rotated to a new slug
- WHEN `/i/k7q2m9xr4t` is requested
- THEN the response MUST render the same friendly contact page shown for a slug that never existed, and MUST NOT render the invitation's content

### Requirement: Rotation invalidates the path-scoped unlock cookie

Because the phone-gate unlock cookie is scoped to the invitation's path
(`/i/[slug]`), rotating the slug MUST make any previously issued unlock cookie
USELESS for reaching the invitation again: the cookie is bound to a path that
no longer resolves, and the new path has never been unlocked by anyone. A guest
who had already unlocked the old link MUST go through the phone gate again at
the new slug. No separate revocation list or cookie invalidation step is
needed or implemented, because the path-scoping already accomplishes it as a
structural consequence, not an enforced rule that could be forgotten.

#### Scenario: A previously unlocked guest must re-unlock at the new slug

- GIVEN a guest unlocked `/i/k7q2m9xr4t` and holds its unlock cookie
- WHEN the slug is rotated and the guest is given the new URL
- THEN visiting the new URL MUST require the phone gate again; the old cookie MUST NOT unlock it

### Requirement: Dispatch history is not deleted by rotation

Rotating a slug MUST NOT delete or alter any `dispatch_events` row belonging to
the invitation. Rotation is a new address for the same invitation, not a new
invitation, and its dispatch history — including that it was sent, opened, or
marked failed — remains true regardless of which slug currently serves it.

This has a direct consequence for deletion: because rotation does not remove
`dispatch_events` rows, a rotated invitation remains just as undispatchable to
delete as it was before rotation (see the invitation-administration
capability's deletion requirement). Rotation is offered specifically because it
is NOT deletion and does not need to clear that history to work.

#### Scenario: Dispatch events survive rotation unchanged

- GIVEN an invitation has a `dispatch_events` row from an earlier send
- WHEN the slug is rotated
- THEN that `dispatch_events` row MUST still exist afterward, unchanged, with the same `invitation_id`

#### Scenario: A rotated invitation remains undeletable if it was dispatched

- GIVEN an invitation with a `dispatch_events` row is rotated
- WHEN deletion of that invitation is attempted afterward
- THEN the deletion MUST still be refused, for the same reason it would have been refused before rotation

### Requirement: A crawler's cached card for the old URL is not invalidated

Rotation MUST NOT be presented, described, or documented as invalidating a
social-media crawler's already-cached preview card for the old URL. Meta caches
a fetched Open Graph card per URL on its own infrastructure and outside this
project's control; once a guest's WhatsApp chat has rendered a card for the old
`/i/[slug]` link, that cached card persists in that chat regardless of what
happens to the slug afterward. This is a real limitation of rotation as a
remedy, not an implementation gap to close, and the system MUST NOT claim
otherwise anywhere a rotation action is surfaced to an operator.

#### Scenario: Rotation's own messaging does not overstate what it fixes

- GIVEN an operator rotates a dispatched invitation's slug
- WHEN the confirmation or resulting UI state is inspected
- THEN it MUST NOT state or imply that the previously delivered message's cached preview card is removed or updated; it MAY state that the link itself no longer works
